# ADR-004 — Cloudinary Owns Production Uploads

- **Status:** Accepted (implemented)
- **Date:** 2026-08-18
- **Context:** Uploads previously wrote to the local `public/uploads` filesystem (`docs/codebase-architecture-audit.md`, `docs/architecture-hardening-report.md`). `app/api/upload/route.ts` now performs server-side signed uploads to Cloudinary: the server computes a SHA-1 signature from the Cloudinary API secret and uploads directly; the secret never reaches the client.
- **Decision:** Production media uploads use server-side signed Cloudinary workflows. Do not restore local filesystem uploads.
- **Rationale:** Cloudinary provides durable, CDN-backed storage; signed server-side uploads keep the API secret server-only; local filesystem uploads are ephemeral and break on serverless deployments.
- **Alternatives:** Direct client uploads with unsigned presets (rejected: weaker control); S3/R2 (rejected: no in-place reason to migrate); local filesystem (rejected and must not return).
- **Consequences:** Uploads require Cloudinary configuration (`NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`); missing config returns 503 rather than falling back to disk.
- **Constraints:** Authenticated access; MIME + extension agreement; magic-byte checks; 12 MB images / 5 MB PDFs; random UUID public IDs; separate folders per content type.
