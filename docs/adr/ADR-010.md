# ADR-010 — Typed Homepage Project Cards and the Beyond Section

- **Status:** Accepted by the owner on 2026-11-15 (not implemented). Conflicts C1–C5 and the open decisions below are still unresolved; implementation phases 2–6 each need their own approval.
- **Date:** 2026-11-15
- **Design source:** Figma "Landing — Desktop", https://www.figma.com/design/chDzSt7d1Nu0QLBwVcwhHc/Untitled?node-id=5-2 (owner-approved as the structural source for this work, per `ARCHITECTURE.md` §11; its type, palette, card treatment and motion remain subject to C1–C3 and C5).
- **Plan:** "Repo Plan: Dynamic Project Cards and Beyond Section" (2026-11-11). This ADR is its phase 1 deliverable.

## Context

The homepage "Selected work" list renders every project with one component (`components/home/FeaturedProjects.tsx`): a numbered label, the description as the headline, tags, a link and one cover image cropped to `aspect-[16/8]`. The proposed redesign gives each featured project a presentation that suits its evidence: phone screens for GoFinancial, a product grid and buyer journeys for Solar-8, a step flow for SecureGate. It also adds a "Beyond product design" section and a brand and graphic design page.

Verified current state (`master` at `3f03359`):

- `Project` has fixed fields only, with no colour or layout field. `ProjectImage` has `url`, `alt`, `caption` and `order`, with no dimensions or role.
- `CaseStudySection` already stores typed `payload` JSON, validated per type in `lib/case-study.ts`, with a fallback to `rich_text` (ADR-003).
- `app/api/projects/route.ts` (POST) and `app/api/projects/[id]/route.ts` (PUT) map each field explicitly. A field missing from either mapping is silently dropped.
- `app/api/upload/route.ts` signs `folder`, `public_id` and `timestamp`, and returns `url`, `filename`, `size` and `type`. The image dimensions in Cloudinary's response are discarded.
- `app/page.tsx`, `app/work/page.tsx` and `app/work/[slug]/page.tsx` are `force-dynamic`. `lib/portfolio-content.ts` uses React `cache()`, which only de-duplicates within one request, so every visit queries the database. (`ARCHITECTURE.md` §3 describes these reads as "cached", which overstates it.) `cacheComponents` is not enabled, so Next.js's previous caching model applies (`node_modules/next/dist/docs/01-app/02-guides/caching-without-cache-components.md`).
- Project writes (POST, PUT, DELETE, images, sections) require any signed-in user, while admin reads check `role === "admin"`. With a single admin account these are equivalent. This is recorded here, not changed.

## Decision

1. **Typed homepage cards, extending ADR-003.** Each project selects one of a fixed set of card templates, and its card content is a JSON payload validated per template by Zod in a new `lib/project-card.ts`. `normalizeCard()` falls back to `media_split`, built from the existing cover image and description, when the payload is missing or invalid. One renderer registry under `components/projects/cards/` renders every template. A new project still needs CMS data only, never a new React page (ADR-001, ADR-006).
2. **Starting template set (ceiling of five):** `media_split`, `device_stage`, `gallery_grid`, `process_flow`, `statement`.
3. **Per-project primary colour.** `Project.primaryColor` stores a hex value. Text colour is not stored: it is computed as the first of white, near-black or black that reaches WCAG 4.5:1 against the primary colour. The admin shows the computed text colour and ratio, and they must match what renders.
4. **Media adapts to what was uploaded.** `ProjectImage` gains `width`, `height` and `role` (`cover`, `screen`, `detail`). The upload route returns Cloudinary's `width` and `height`. Cards choose columns from the image count and aspect ratio from stored dimensions, and do not crop interface screens.
5. **Hierarchy fix.** The project title leads each card and the description is subordinate. This replaces the current description-as-headline pattern.
6. **Beyond and brand work.** Beyond rows are `SiteContent` validated by a Zod schema and edited in the existing content admin. Brand and graphic projects reuse `Project` with `collection = "brand"` (pending decision 2), listed on a new public page.
7. **Additive schema change only.** One migration adds `Project.primaryColor String?`, `Project.cardTemplate String @default("media_split")`, `Project.cardPayload Json?`, `Project.collection String @default("product")`, and `ProjectImage.width Int?`, `height Int?`, `role String?`. Nothing is renamed, dropped or backfilled, following `20260814000000_evolve_case_study_sections`.

## Rationale

- Extends a pattern the repository already trusts (typed payloads, Zod validation, safe fallback) instead of adding free-form layout control or per-project code.
- Contrast is computed rather than chosen, so a colour picked in the CMS cannot produce unreadable text.
- Stored image dimensions remove manual grid fitting and stop interface screens being cropped.

## Alternatives considered

- **Per-project React components:** rejected; violates ADR-001 and ADR-006.
- **Free-form layout builder in the admin:** rejected; unbounded, hard to validate, and weakens the editorial consistency ADR-005 requires.
- **Reusing `CaseStudySection` for the homepage card:** rejected; the card is one per project and appears outside the case study, so it is clearer as project fields.
- **Storing the text colour:** rejected; it could drift from the primary colour and fail contrast.

## Consequences

- Adding a template requires a schema in `lib/project-card.ts` and a renderer component, as ADR-003 requires for section types.
- Both project API mappings must include every new field; tests must cover save-and-reload so no field is silently dropped.
- Any new Cloudinary upload parameter must be added to the signature string. The existing upload validation (SEC-INV-006) is unchanged.
- `ARCHITECTURE.md` §4, §5, §9 and §14 must be updated when, and only when, the change is implemented.

## Constraints

- Legacy projects with no card data, payload or image dimensions must render through the fallback.
- New write paths keep the existing `auth()` checks and return `401` to anonymous users (SEC-INV-002, SEC-INV-008). No security test is weakened.
- Unpublished projects stay private (SEC-INV-003), including in any new brand listing.
- Uploads remain Cloudinary server-side signed (ADR-004).
- Production migration, deployment and activation of the new look are separate owner approvals (plan phase 6), with a database backup and a rollback plan.

## Implementation phases (each needs its own approval)

1. Decisions and this ADR (documents only).
2. Schema, migration file, `lib/project-card.ts`, validation and unit tests, against a local or test database only.
3. Admin card editor and API mappings, image role and dimensions, upload dimension capture.
4. Card renderer and homepage change, tested locally.
5. Beyond content schema and the brand collection page.
6. Production migration and deployment, then activation.

Checks at the end of every phase: `npx tsc --noEmit`, `npm run lint`, `npm test`, `npm run build`, and a reviewed diff.
