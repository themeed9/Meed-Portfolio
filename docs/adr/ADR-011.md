# ADR-011 — Case-Study CMS Layer: Block Media, Layout and Form Editing

- **Status:** Accepted. The owner approved the four-step plan on 2026-11-19 ("Proceed with steps") and asked that every section can take images or be text only. Implemented on branch `agent/case-study-cms`.
- **Date:** 2026-11-19
- **Extends:** ADR-003 (typed case-study blocks). Does not replace it: the 19 block types, their payload schemas, `normalizeSection()` and the `rich_text` fallback are unchanged.

## Context

ADR-003 gave case studies typed, ordered blocks, but the admin edited each block's payload as raw JSON. Block media was a single image (`imageUrl`), only used when a block had no valid payload. The page always rendered the legacy `overview` and `challenge` fields under fixed headings ("The product in context.", "The product challenge."), which the owner could not change or remove. There was no per-block control of width, background or visibility, no starter templates and no preview of unpublished work.

## Decision

1. **Form editing.** `lib/case-study-blocks.ts` holds a field spec (`TYPE_INFO`) for every block type. The admin (`components/admin/CaseStudySectionEditor.tsx`, `components/admin/case-study/BlockFields.tsx`) renders real fields from it: text, long text, single media, media lists, string lists and repeatable rows. JSON is never shown.
2. **Media on every block.** Each block can carry up to 12 images, GIFs or videos, or none (text only). Media live in `CaseStudySection.metadata.media` with alt text (required), caption and display fit. The legacy `imageUrl` becomes the first media item when read, and is cleared on the next save so it is never shown twice.
3. **Per-block settings** in `metadata`: `mediaLayout` (below, above, left, right, grid), `width` (default, text, wide, full), `background` (plain, tint, project colour with the auto-picked AA text colour from `cardColors`), `hidden` and `showInContents`. Invalid settings fall back to defaults when read; they are rejected when written.
4. **Visibility rule.** A public block must have every required field filled (`missingRequiredField`, because the ADR-003 schemas accept empty strings). A hidden block is a draft and may be incomplete. Media and settings are validated in both cases. `checkBlock()` is used by the editor and by the section API routes.
5. **Legacy text to blocks.** `POST /api/projects/[id]/sections/starter` with `{ legacy: true }` creates `rich_text` blocks for non-empty legacy fields, first in order and marked `metadata.legacy`. Overview and Challenge, already public, stay visible with their old headings. Approach, Results and Testimonial were never rendered publicly, so they arrive hidden for review. Nothing is deleted. The page stops rendering a legacy field only once a block marked with it exists, so there is no data migration and no deploy-order risk.
6. **Templates.** The same endpoint with `{ template }` appends a starter set (product case study, brand project, short case study) as hidden drafts.
7. **Page extras.** "On this page" (three or more titled visible blocks), read time, contribution and tools in the header facts, a "Next project" link in CMS order, and the hero or cover image as the share image.
8. **Preview.** `/admin/projects/[id]/preview` renders any project, published or not, including hidden blocks with a "Hidden draft" label. It is admin-only (proxy plus a server-side role check) and `noindex`.

## Security

- Block media URLs must be site-relative paths, `https://res.cloudinary.com/` or `https://images.unsplash.com/`: the same hosts the Content-Security-Policy and `next/image` allow (`isAllowedMediaUrl`). `javascript:`, `data:`, plain `http:`, protocol-relative and look-alike hosts are rejected, including in drafts. Covered by `tests/security/case-study.test.ts`.
- Section writes keep their existing session check. Uploads still go through `app/api/upload` (SEC-INV-006); videos are linked from Cloudinary, not uploaded here.

## Consequences

- No database migration: everything new lives in the existing `metadata` JSON column.
- Adding a block type still means a schema in `lib/case-study.ts`, a renderer branch, and now a `TYPE_INFO` entry. Tests fail if a type has no field spec or its filled spec does not validate.
- The legacy `overview` and `challenge` fields remain in the schema and the project form until the owner has converted every project; removing them would be a separate, approved migration.
- Fixed a long-standing bug: `rich_text` blocks rendered as a labelled "BODY" field; they now render as prose.
